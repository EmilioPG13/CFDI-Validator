# `api/` — the one non-static piece of this deployment, and it's 100% generated

`api/` itself holds no hand-authored source anymore — everything here is `esbuild` output.
The real source lives in **`api-src/`**. Don't hand-edit anything under `api/`; edit
`api-src/` and rerun `npm run dev`/`npm run build` (or `node scripts/bundle-api.mjs`
directly) — **then commit the regenerated `api/*.js`(`.map`)**. Unlike every other
generated artifact in this repo, these files are deliberately tracked in git, not
gitignored — see the "Why committed, not gitignored" note below.

`api-src/consulta-sat.ts` is a Vercel Function (`export const config = { runtime: "nodejs" }`)
proxying SAT's `ConsultaCFDIService` for the two live SAT-sourced rules
(`cfdi-cancelado-sat`, `emisor-efos-69b-sat`). It exists only because that SAT endpoint
sends no `Access-Control-Allow-Origin` header — confirmed live, 2026-08-06 — so a browser
can never call it directly; everything else in this project runs as static WASM in the
browser with no backend at all. See `CLAUDE.md` and the project plan for the full
architecture reasoning.

## Why `api/` is pre-bundled instead of deployed as source (Phase 4g)

`api-src/consulta-sat.ts` imports `sat-client`'s `ConsultaCfdiClient` via a plain relative
path (`../../sat-client/src/consultaCfdi.ts`) — the same monorepo-relative-import pattern
`engine/src/rules/index.ts` uses successfully for `engine` ↔ `sat-client`. That pattern works
fine for the main `frontend` build (Vite bundles it, proven in a real `npm run build` since
Phase 4e) but **does NOT work for either of Vercel's zero-config API function builders** —
confirmed with two separate real failed deploys, not assumed:

- **Edge runtime** (the original choice): fails at **deploy** time. Its bundler won't inline
  a relative import living outside the function's own directory, even with
  `sourceFilesOutsideRootDirectory` on and the file physically present during the build —
  `NOW_SANDBOX_WORKER_EDGE_FUNCTION_UNSUPPORTED_MODULES: "referencing unsupported modules:
  .../consulta-sat.js: ../../sat-client/src/consultaCfdi.ts"`.
- **Node.js runtime** (switched to, still as raw source): deploys successfully — but then
  fails at **runtime**, on the very first invocation. Vercel transpiles only the entrypoint
  `.ts` file to `.js`; it does not bundle the transitive `.ts` import, so the deployed
  function crashes with `Error [ERR_MODULE_NOT_FOUND]: Cannot find module
  '/var/task/sat-client/src/consultaCfdi.ts'`.

Both failures are the same root cause from two different angles: neither builder does a
real esbuild-style dependency walk for a monorepo-external `.ts` file. The fix is to remove
the need for either builder to do that at all — `scripts/bundle-api.mjs` runs `esbuild` with
`bundle: true` over `api-src/*.ts` *before* Vercel's own build/function-detection step runs
(wired into `prebuild`, same as `sync-static-assets.mjs`), producing a fully self-contained
`api/*.js` with every local import already inlined. `sat-client` has zero external
dependencies and `consultaCfdi.ts`'s only local import is `rateLimiter.ts` (also
zero-import), so there's nothing left for Vercel's builder to fail on — verified by
importing the bundled `api/consulta-sat.js` directly in a plain Node process and invoking
its default export with real `Request` objects (OPTIONS preflight, a validation-error POST)
before ever pushing to Vercel.

See `frontend/vercel.json` for the full monorepo build config (install chain across
`engine`/`sat-client`/`frontend`, Node version pin, `sourceFilesOutsideRootDirectory` is
still needed so the *main* Vite build can read `../corpus`/`../engine`/`../sat-client`) and
`CLAUDE.md`'s "Vercel deployment config" gotcha for the full incident history.

## Why `api/*.js` is committed, not gitignored (deploy #4)

The pre-bundling fix above was necessary but not sufficient. Deploy #4 kept the generated
output gitignored (regenerated by `prebuild`, same pattern as `engine/catalog-bundle/`
elsewhere in this repo) — and got a clean `404 NOT_FOUND` on `/api/consulta-sat` despite a
fully successful build. The build log made the reason visible: every prior deploy showed a
distinct "Installing dependencies... Using TypeScript..." step where Vercel processed
`api/`'s function(s); this one didn't have it at all. **Vercel decides which files under
`api/` are functions by scanning the git checkout before running any install/build
command** — a file that `scripts/bundle-api.mjs` only produces mid-build (during
`prebuild`) doesn't exist yet at that scan, so Vercel plans zero functions for the
deployment, and the route 404s even though `api/consulta-sat.js` is sitting right there in
the build output by the time the build finishes. `outputDirectory` (`dist/`) does NOT work
this way for static assets — only `api/` function detection has this earlier scan. Fix:
`api/*.js`(`.map`) are committed directly, so they're already present at the point Vercel
scans, and `bundle-api.mjs` stays wired into `predev`/`prebuild` purely so local dev/CI
never runs against a stale bundle — that does not replace the commit step.

## Local testing

`api-src/consulta-sat.test.ts` unit-tests the HTTP-handling wrapper (method/body validation,
response shaping, CORS headers) using Node's global `Request`/`Response` and an injected
fake `consultaFn` — it never hits the real network, and it tests the real hand-authored
source directly, not the bundled output. `ConsultaCfdiClient` itself (the actual SOAP call,
rate limiting, retries) is already covered by `sat-client/test/`, including live calls
against the real SAT endpoint — not re-tested here.

Run with `npm run test` from `frontend/` (same `node --experimental-strip-types --test`
convention as `engine/` and `sat-client/`).
